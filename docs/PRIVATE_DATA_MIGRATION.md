For the PostgreSQL adapter added in Phase 1D, see [Database architecture](DATABASE_ARCHITECTURE.md). The browser preview below remains read-only.

Phase 1C provides a counts-only browser preview and an archive import service contract. The app has no business database binding and cannot import live records. ## PostgreSQL design

Use a Node-only repository via the existing Next.js API on the original Vercel project. Bind one server-selected workspace and derive identity from the existing authenticated principal. Use a least-privilege runtime role, a separate schema-migration role, parameterized statements, TLS with certificate verification, and environment-specific pooled connections. Private file storage must be authenticated, encrypted, and distinct from public static assets. Keep raw provider credentials in approved server secret storage. Redis remains responsible for security state.

| Proposed table | Keys, fields and boundaries |
| --- | --- |
| `workspaces`, `workspace_members` | UUID workspace key. Membership key `(workspace_id, principal_id)`, with server role and lifecycle. No browser-auth material. |
| `agents`, `workflows`, `workflow_versions` | Workspace-scoped UUIDs. Workflow FK to agent. Version FK to workflow and unique version number. Immutable published graph `jsonb`, checksum, author and timestamps. Draft/current references separate from historical versions. |
| `workflow_runs`, `workflow_steps` | Version FK and execution idempotency key. State transitions, timestamps, safe diagnostics, restricted step inputs/results. Legacy runs are archive history. |
| `sources` | Agent FK, private blob locator, MIME, size, SHA-256, upload and retention metadata, and upload/verification state. Make metadata visible only after object verification. |
| `approvals` | Run and step FKs, protected action digest, actual server approver, timestamps and state. Imported reviewer text remains historical and cannot authorize anything. |
| `calendar_entities`, `calendar_entries`, `workflow_schedules` | Workspace-scoped entities/dates/notes and workflow version schedule configuration. Explicit time zone, next-run and enabled state. Historical schedules start disabled. |
| `contacts`, `whatsapp_templates`, `whatsapp_campaigns` | Workspace ownership, private contact data and consent, immutable template versions, campaign state and explicit audience provenance. |
| `reminders`, `message_attempts` | FKs to contact/campaign/template as applicable. Idempotency key, timestamps, outcome and redacted error metadata. No jobs or sending in this phase. |
| `admin_audit_events` | Append-only server actor, operation, target ID, timestamp and result counts or codes. Exclude body content, credentials and phone numbers. |
| `legacy_import_records` | Unique `(workspace_id, kind, legacy_id)`, format version, inert `jsonb` payload, SHA-256 and first batch membership. Scope reads and writes to the same workspace; archive rows are not operational tables. |
| `legacy_import_batches`, `legacy_import_entries` | Unique `(workspace_id, manifest_sha256)`, approval actor/time and outcomes, plus per-record references to distinguish new versus reused rows. Persist receipt and membership atomically with rows. Support audited quarantine and prevent replay of an explicitly rolled-back batch. |

Use workspace-scoped composite foreign keys for business relationships. Enforce uniqueness and use insert-on-conflict without updates for archive deduplication. The adapter must pin one connection for the whole transaction. Compare read-back canonical JSON and digest before commit, use one verified receipt per manifest, and block on a conflicting ID. Prefer a least-privilege pool with bounded transaction timeouts and test races on the selected provider. No DDL or connection exists in this phase. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) · [INSERT conflict semantics](https://www.postgresql.org/docs/current/sql-insert.html)

## Procedure and integrity contract

1. Open **Data migration** under the private workspace using the server account identified by `GRA_WHATSAPP_ADMIN_ID` and role `admin`. Other accounts, scoped tokens and unauthenticated requests cannot use the page or import API. Existing session checks, same-origin mutation requirements and limits remain in force.
2. Click **Preview this browser**. The browser reads known keys and opens an existing source database in a read-only transaction. It displays counts for valid shapes, invalid records, unreadable storage entries and excluded keys. Deferred shapes receive a structural review only. Missing IndexedDB enumeration support appears as unreadable. The page cannot confirm that a profile is clean if inspection is incomplete.
3. Resolve malformed, orphaned, conflicting, unsupported and oversized candidates against an encrypted backup before future approval. The current archive contract accepts up to 250 agents/graphs/version records and a 1 MiB JSON request. Validate linked agent IDs and graph endpoints. Candidate status is structural eligibility for an archive. It is not a statement that a workflow is production-ready. Source/file references are not resolved by this archive phase.
4. After a durable adapter is reviewed and bound, add the explicit approval UI for a freshly read, frozen batch. Require confirmation for the exact canonical record manifest, identified by its schema-bound SHA-256. Close other private tabs before taking the snapshot so concurrent browser edits can be detected or avoided. Exclude unsupported categories visibly rather than sending them accidentally. The current UI and API remain preview-only.
5. A future adapter must insert absent archive rows, report already identical rows, and reject conflicting identities without overwriting. Verify every persisted row against the approved payload before recording a successful receipt. Validation, conflict, integrity, or receipt errors must leave the transaction uncommitted. A dropped commit acknowledgement is indeterminate until the same approved manifest is safely reconciled or retried. API results contain counts or safe error codes only.

## Encrypted backup and rollback

Inventory each authorized browser profile and device, including old origins where relevant. Have the owner approve a backup and retention plan before verifying any live archive. Export selected raw values and file bytes only through approved tooling that encrypts before writing or transfer, with an access-controlled key held separately and authenticated encryption or an equivalent managed backup control. Verify record counts and privately held checksums, document provenance and demonstrate restore with synthetic fixtures. Never include session cookies or client secrets in business exports. Handle legacy credential artifacts under a separate remediation policy, including rotation where appropriate. [PostgreSQL backup and restore](https://www.postgresql.org/docs/current/backup.html)

Keep browser originals through verification and recovery drills. A fail-closed transaction rolls back uncommitted writes. For a committed batch, a future authorized rollback must quarantine only records first introduced by that batch, retain referenced or promoted rows, and record a tombstone in the audit trail. Backup restores and cleanup are manual, separately authorized operations. This phase supplies no exporter, schema runner, profile cleanup, or rollback endpoint.

## Future configuration and release checklist

- [ ] Identify the existing Vercel project by its assigned production domain. Confirm Production auth, Redis, exact origin and the designated administrator.
- [ ] Approve PostgreSQL provider, data residency, retention, private file service, pooled TLS connection, least-privilege roles and encrypted backups. Provision server-only connection settings after authorization.
- [ ] Review and test the database adapter, schema, conflict races, connection loss, rollback, access controls and restore in a non-production database.
- [ ] Replace ongoing confidential browser writes with authenticated server persistence. Migrate files and the deferred categories with their own integrity checks. Keep live workflows and credentials out of migration replay.
- [ ] Build and verify administrator approval and recovery flows. Reconcile a signed inventory of each authorized device and profile before approved cleanup. One browser preview or receipt proves nothing about other profiles.
- [ ] Verify public isolation and private access before approving a production release. Same-origin browser persistence is still a release blocker.
